# 0001. Modular monolith with multiple entrypoints (api, ingestor, worker)

## Context and problem statement

The hub has three very different runtime profiles:

- **HTTP/WebSocket API**: latency-sensitive, request/response, scales with users.
- **Telemetry ingestion**: a long-lived MQTT consumer that batches writes. It scales
  with device count and must keep absorbing load when the API is busy (and the
  other way round).
- **Background work**: outbox relay, scheduled automations, notifications and
  command timeouts. Bursty, and it must not run inside a request.

The business rules behind them overlap. Ingesting telemetry updates the device
twin (`devices`) and can fire automations (`automations`), which send commands
(`commands`). How do we deploy these profiles independently without splitting the
domain into services before its boundaries have been proven?

## Decision drivers

- Independent scaling and failure isolation for ingestion vs. the API.
- One place to change a business rule, with refactoring checked by the compiler and type checker.
- Module boundaries that are enforced, not aspirational, so a later extraction
  into a service stays cheap.
- A local stack small enough to run on a laptop.

## Considered options

1. **Single process** running API, MQTT consumer and scheduler together.
2. **Microservices**: one service per bounded context, each with its own codebase.
3. **Modular monolith with multiple entrypoints**: one codebase and one deployable
   image per entrypoint, each process wiring only the modules it needs.

## Decision outcome

Chosen option: **3, modular monolith with multiple entrypoints.**

- `apps/api/src/smarthome` holds every module (`identity`, `devices`, `telemetry`,
  `commands`, `automations`, `notifications`, `energy`) plus a small `shared` kernel.
- `smarthome.main:create_app` is the composition root for HTTP. `apps/ingestor`
  and `apps/worker` are thin packages with their own composition roots; they
  depend on `smarthome-api` as a Poetry path dependency and import the same modules.
- `apps/simulator` does **not** depend on the monolith, only on
  `packages/device-protocol`, exactly like a real device would.

### Module rules

- Every module has the layers `api → infrastructure → application → domain`.
  A layer may import the layers below it, never the ones above.
- `domain` imports no framework (`fastapi`, `starlette`, `sqlalchemy`, `pydantic`,
  `redis`) and no shared infrastructure.
- A module reaches another module only through `modules/<x>/public.py`, or
  asynchronously through domain events delivered by a transactional outbox
  (introduced with the first cross-module event).
- `shared` never imports a module; modules never import an entrypoint.

### Persistence rules

- One Postgres schema per module, created by migration `0001`. No foreign keys
  across schemas; cross-module references are plain ids.
- **One Alembic history** for the whole monolith, version table in `public`.
  Several histories (one per module) would mean deciding the order between modules
  on every deploy, and nothing is gained while everything ships as one artifact.
  If a module is extracted, its schema moves out together with its migrations.

### Consequences

- Good: the ingestor can be scaled to N replicas and restarted without touching the API.
- Good: a rule such as "telemetry over a threshold triggers an automation" is
  plain function calls and events inside one codebase, testable without a network.
- Good: extracting a module later is a mechanical change. Its `public.py` becomes a
  client, its events already travel through the outbox, and its schema is already
  separate.
- Bad: every entrypoint image carries every module's code and dependencies.
  Acceptable at this size; revisit if image size or cold start matters.
- Bad: the boundaries hold only as long as the tooling enforces them. Hence the
  confirmation below.
- Bad: Poetry does not resolve path dependencies transitively, so `ingestor` and
  `worker` repeat `device-protocol` in their own `pyproject.toml`.

### Confirmation

- `apps/api/.importlinter`, generated by `scripts/gen_import_contracts.py` (one
  `forbidden` contract per module, a `layers` contract over all modules, plus the
  domain-purity, shared-kernel and entrypoint contracts). CI fails if the file is stale.
- `tests/architecture/test_import_contracts.py` injects each kind of violation into
  a copy of the source tree and asserts the matching contract breaks. That proves the
  contracts reject bad imports, not just that today's code passes them.

## Pros and cons of the options

### 1. Single process

- Good: simplest to run.
- Bad: an ingestion spike (thousands of simulated devices) degrades API latency, and
  a crash in the consumer takes the API down with it.
- Bad: scheduled jobs run once per API replica unless leader election is added.

### 2. Microservices

- Good: hard boundaries, independent deploys.
- Bad: boundaries drawn before the domain is understood are expensive to move.
  Every cross-context rule becomes a network call or a saga.
- Bad: the operational surface (N pipelines, N databases, contract versioning)
  would dominate a project whose point is the domain and the data flow.

### 3. Modular monolith with multiple entrypoints

- Good: process-level isolation where the runtime profiles differ; code-level
  cohesion where the rules overlap.
- Bad: needs discipline, which here is enforced by import-linter in CI.
